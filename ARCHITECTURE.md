# How the app works — and what each change touches

This guide explains **what the app does, how it does it, and why**, so that before you change something you can tell
what it affects. It complements [CONTRIBUTING.md](CONTRIBUTING.md) (how to contribute, file tables, data corrections);
read this first if you are about to touch the engine, the data loading or the roster.

It is organised around questions: *where does a unit's data come from? what is a roster entry? how is a profile, a price and a legality check
produced? which concepts cross each other (slots, allies, keywords, marks...)? what are the special cases? how do I check I did not break
something?* The last sections are short lookup tables: **"I want to change X → where"** and **"If I touch X → check Y"**.

> File paths are relative to the repository root. Line numbers are deliberately not used: they move every week. Search for the name.

---

## 0. The five rules that prevent most bugs

1. **One question, one place.** If the same question ("is this unit allied?", "does it have this keyword?", "what abilities does this weapon show?")
   is answered in two places, they will drift. Use the existing helper; if there is none, add one and move the old checks onto it.
   (We removed ~40 copies of "is this unit allied" this way: `isAlliedEntry`.)
2. **Keyword lists that are compared in lower case are built by one function.** Never mix raw strings ("Cataphractii") with already-lower-cased ones.
   This exact mistake kept four weapons locked for a week (GitHub #292).
3. **The sheet is the source of truth, not the app.** If a datasheet or the Armory is wrong, the fix is in the Google Sheet (or reported to its
   author), not a patch in the app. Unit files are regenerated by a script and your edit will be overwritten (see §2).
4. **Test through the real code path, not a hand-made list.** Build the entry, call `resolveUnitProfile` / `computeUnitPoints` / `validateArmy`,
   and compare **before and after for the whole game**, not only for the unit in the report (see §9). Spot checks have hidden regressions every time.
5. **Prefer data- or text-driven rules over rules keyed by a name** ("if the unit is called X"). When a name table is unavoidable, add it to the
   catalogue in §6 with a comment saying why.

## 1. The big picture

```
 Google Sheets (the codices, written by the rules authors)
        │   UnwiseGetData/ script ("Run unit update" button → GitHub Action → PR)
        ▼
 data/parsed/<faction>/…json   (units, armory, archetypes, psychic…)      ← the app's data
        │   src/data/loaders.ts   (loads one faction, then NORMALISES it — §2)
        ▼
 FactionData  ──►  src/store/army.ts  (zustand: the ArmyState and its RosterEntry[] — §3)
                          │
                          ▼
        src/engine/  — three questions about a roster entry (§4)
          resolver.ts   "what does this unit look like?"  → ResolvedProfile
          points.ts     "how much does it cost?"          → number
          validators.ts "is the army legal?"              → ValidationItem[]
                          │
                          ▼
        views — all read the SAME ResolvedProfile:
          UnitCard (builder) · ArmoryModal · PrintView · PlayView/battle view (lib/battleProfile.ts) · TTS export (utils/ttsExport.ts) · ReviewStep
```

The key design idea: **the engine computes, the views only draw.** The unit card, the printout, the battle view and the Tabletop Simulator export
all call `resolveUnitProfile`, so a rule fixed in the resolver is fixed everywhere at once. The flip side: a change in the resolver changes
*every* view and *every* faction, which is why §9 insists on whole-game comparisons.

Around that core: `src/i18n` (5 languages), `src/data/changelog.ts` and `LandingPage.tsx` (release notes / banner), `api/` (serverless
functions: saves, leagues, Gitfinda; hard cap of 12 functions), `wiki/` (separate Astro site), `tts/` (Tabletop Simulator mod).

## 2. The data: what a unit is, who owns it

### 2.1 The shapes (`src/types/data.ts`)

| Type | What it is | Notes |
|---|---|---|
| `FactionData` | One codex, loaded: `units`, `slot_to_units`, `armory_general`, `armory_marks`, `armory_legions`, `archetypes`, `legacies`, `traits`, `disciplines`, `animosity`, `allied`… | Built by `loaders.ts` |
| `Unit` | A datasheet: `models`, `weapons`, `equipped_with` (text), `option_groups`, `abilities` (text lines), `keywords`, `unit_type`, flags (`is_character`, `is_vehicle`, `has_armory_access`, `advisor`…) | The unit's loadout is **text** (`equipped_with`) plus a weapon catalogue; the resolver reads it |
| `Model` | One row of the unit (name, min/max, points, stats) | A promoted model (Exarch, Sergeant) is in `variant_models` |
| `Weapon` | One weapon **profile** row | A weapon with several firing modes is several rows (`Name - Mode`); see §5.5 |
| `OptionGroup` | One option line of the datasheet: header, `constraint` (`one`, `every`, `per_n`, `fixed_max`, `unique_upgrade`, `mark`…), `choices`, `replaces`, `inline_pts`, `variant_link`, `applies_to_model`, `requires_*`, `available_if` | Choices are **indexed**: see §3.2 |
| `ArmoryItem` | An Armory entry: `desc` (the rule text), prices (`p_unit`, `p_char`, `p_veh`), gates (§5.3), optional `effect` (stat mods, granted weapons/abilities) | Items are in sections `weapons`, `equipment`, `daemon_weapons` |
| `ArchetypeRule` | What an archetype changes (`src/engine/archetypes/base.ts`) | §5.4 |

### 2.2 Ownership — read this before editing any JSON

* **Unit files (`data/parsed/<faction>/units/**`) for the 19 sheet-driven codices are written by Unwise's script** from the live sheets
  (button "Run unit update" → GitHub Action → a PR). **A hand edit to a unit file is lost the next time the script runs.**
  What is fixed in the sheet is fixed for good; what is fixed in the JSON is fixed until the next update.
* The Armory, archetypes and psychic files are hand-maintained today, **but follow the sheet**: the `.ods` in `Codex/` is the canon for facts
  (stats, points, weapon names). The app's own semantics (what a rule *does*) live in the engine.
* The canonical rules are the Core Rules and the Missions (`Codex/*.docx`, refreshed with `node scripts/fetch_docs.cjs --write`). **Codex rules
  beat Core Rules** (FAQ #5). Do not decide a rule "from memory of the real game": this is a homebrew and the real-game rule often differs.
* If the script writes something odd (e.g. a weapon header without `*` leaves loose "- Ranged" rows), **report it to the sheet author**; do not
  special-case it in the app.

### 2.3 The loader safety net (`src/data/loaders.ts`)

After a faction is loaded, `FACTION_LOADERS` runs normalisers so the script's output format cannot matter. In order:
`aliasRenamedUnits` (old unit names in saved lists) → `normaliseMonsterFlag` → `normaliseKeywordList` (the script writes "Cultist, Death Guard" as one
keyword: split) → `normaliseEveryModelPick` → `linkSharedCapGroups` → `applyArmoryModelTypes` → `applyTextGates` (Armory restrictions read from the
item text, `src/data/textGates.ts`) → `applyIntrinsicAllies` → faction extras → `applyDataOverrides` (admin corrections stored in the DB; ignored for
factions the script owns).

**Rule of thumb:** a fix for "the data comes out in a shape the engine does not expect" belongs in a loader normaliser (it survives every update).
A fix for "the data is wrong" belongs in the sheet.

## 3. The roster and the store

### 3.1 `RosterEntry` (`src/types/army.ts`) — one unit in the list

`id`, `unitName`, `slot` (the slot it was added in), `size` (and `modelSizes` for units made of several model groups), `mark`, `optionQty`, `armory`
(`ArmorySelection[]`), `traits` (derived, see below), `powers`, `prayers`… and the fields that say **where the unit belongs**:

| Field | Meaning |
|---|---|
| `factionSource` | Undefined = the army's own codex. A slug (`'inquisition'`, `'assassins'`…) = the datasheet comes from **another codex** (read from `data.allied[slug]`). |
| `ownArmy` | The unit was added from the **main** list although its codex is another one (an archetype/legacy grants those units). It matters when that codex is also the ally's. |
| `nestedFaction` | Second-level ally: where the unit's DATA is read from (an ally's own archetype grants another codex). Not used to decide which rule applies. |

Never test `factionSource === alliedFaction` yourself: use `isAlliedEntry(item, alliedFaction)` (`src/types/army.ts`) and, for "which archetype governs this
unit", `effectiveArchetypeFor(item, state)` (`src/engine/points.ts`).

### 3.2 `optionQty` is indexed — never reorder

`item.optionQty[groupIndex][choiceIndex] = qty`, and `'__inline'` for a tick-box group. **The indices are positions in the datasheet's
`option_groups` / `choices`.** Inserting or reordering a group or a choice silently moves every saved list's selection onto a different option.
New choices go at the **end**; removed ones need a migration (see `src/engine/unitRenames.ts` and the migrations in `store/army.ts`).

### 3.3 Derived state in the store (`src/store/army.ts`)

`item.traits` is **not** a user choice: `applyArmyTraits` recomputes it from the army's trait pool every time something that can change it moves
(trait pool, archetype, a unit's mark, subfaction…). Which units get a trait, and what it costs, is decided there (e.g. Chaos Space Marines: only
models with the `Chaos Space Marine` keyword). If a unit "pays for a Trait and gets nothing", or "gets none", look here first and then at the keyword
(§5.2).

The store persists to `sessionStorage` with a **version and migrations** (`persist` `version`, `savedFormat`); loading an old list goes through
`migrate()` / `importRoster()`. A change that alters the meaning of a saved field needs a migration.

## 4. The engine in three questions

### 4.1 "What does this unit look like?" — `resolveUnitProfile` (`src/engine/resolver.ts`)

Input: `(item, unit, state, data)`. Output: a `ResolvedProfile` (stats rows, weapons and their counts, abilities, psyker flags, notes…). Stages, in order:

1. **Gated option groups** are dropped from the selections (`requires_trait` / `requires_archetype` / `requires_legacy`): the selection stays in the save and
   simply stops applying.
2. `expandAllRemaining` — "All remaining models may swap…" is expanded to the right number.
3. **`resolveBase`** — the big one. In this order it works out: marks, variants (promoted models), psyker status, the weapon catalogue, **trait effects**
   (`traitEffects.ts`), **Armory purchases** (`equipMods.ts` parses stat modifiers and quoted abilities from the item text; items that grant weapons; items
   aimed at one weapon; named weapon families), **option effects** (`effect.stat_mod`, `grants_abilities`, `grants_weapons`), abilities granted "for all
   melee/ranged weapons", Exarch powers, deployment rules, rule notes.
4. **A faction resolver** (`FACTION_RESOLVERS`: Chaos Space Marines, Chaos Daemons, Space Marines, Adeptus Mechanicus) adjusts the result.
5. `computeWeaponsToShow` → which weapon rows exist at all (an optional weapon appears only once bought).
6. `computeWeaponGroups` → the weapon **tables** (one per model row when the loadouts differ), `computeModelRowCounts`, `fillMissingWeaponCounts` → the
   "Nx" in front of every row.

**Weapon abilities** deserve their own paragraph because many code paths write them. Abilities are collected in a map (`weaponTraitMap`: weapon name →
extra abilities; `championWeaponTraitMap` for the champion's own copy) from about nine places (traits, Armory items worded "All X weapons gain…", items aimed
at one weapon, named options, Exarch powers, family boosts, the generic "for all melee/ranged" parser…). **The single point where they become text is
`mergeWeaponAbilities` (`src/engine/abilityMerge.ts`)**: it lists an ability once and keeps the best value (`Poison(3+)` beats `Poison(4+)`, `Deadly(4+)`
beats `Deadly(5+)`). So adding the same ability from two places is harmless; adding it from a *new* place that the merge does not see is not.

Stat conventions you must know: values printed as `3+` (SV, BS, WS) are stored in **printed-number space**, so an *improvement* is a **negative**
delta (`+1 BS` = `-1`) and a penalty is positive (Daemonic possession: BS/WS `+1`). Plain numbers (S, T, A, LD…) are ordinary. Caps: S/T/I/A/LD stay between 1 and 10
(`src/lib/statPipeline.ts`, applied in every view).

### 4.2 "How much does it cost?" — `computeUnitPoints` (`src/engine/points.ts`)

Base model costs (or the variant's), option choices and inline options, Armory purchases (some scale per model/per wound), traits, marks, legacy/archetype
extras, deployment rules bought per wound. It reads the same selections as the resolver, so **a selection that changes the profile but not the price (or the
other way round) is a bug**. When you add a new kind of selection, check both.

### 4.3 "Is the army legal?" — `validateArmy` (`src/engine/validators.ts`)

Returns a list of `{ type: 'error' | 'warn' | 'info' | 'ok', text }`. Sections, roughly: points; slots and AOPs; engagement rules (Skirmish caps);
archetype/legacy/trait constraints; per-unit option constraints; allies; faction-specific rules (Daemonkin, Entourage, Platoons…). Slot counting is
`getSlotUsage` and the AOP logic `getAopState` — both are shared with the Slot panel so the screen and the validator cannot disagree.

**The UI gates and the validator must agree.** The UI hides or greys things ("soft" rules); the validator reports them if they are in the list anyway
(loaded, imported, or made legal by another change). When you add a restriction, add it to both, or to the shared helper both use.

## 5. Concepts that cross each other

### 5.1 Slots and AOPs

A unit's slot is decided in a chain; each step can change it:

`printed slot` → **archetype remap** (`getEffectiveSlotFor`, `archetypes/index.ts`: `troopsRemap`, `elitesRemap`, `hqPromotion`…) → **datasheet overrides**
(`applyVariantSlotOverride`, `slotOverrides.ts`: an upgrade that makes the unit HQ — Chief Apothecary, Ascended Daemon Prince; an opt-in; a biomorph such as
Winged that moves Troops to Fast Attack; an archetype that already remaps the unit wins) → **platoon** (a unit linked to a Platoon Command Squad shares its slot)
→ **free-slot exemptions** (Advisor `advisorExemptIds`, Entourage/Herald, Assassins, Retinue, Royal Court…) → counted in `getSlotUsage` → compared with the
engagement's AOP (`engagements.ts`) and `getAopState` (a full AOP unlocks the next one).

### 5.2 Keywords

A unit's keywords are **computed**, in one function: `effectiveKeywords(unit, entry, rule, extra)` (`src/engine/keywords.ts`), always **lower-cased**:
datasheet `keywords` + unit types + flags (Psyker, Vehicle…) + roles derived from the name (`ROLE_KW_FROM_NAME`, legacy) + the entry's Mark + armour keyword
(innate or **bought**: Cataphractii and Tartaros also count as Terminator) + keywords granted by the army's archetype (`ArchetypeRule.grantsKeywords`, e.g.
Legion CSM: a Horus Heresy unit with a Mark is a Chaos Space Marine).
`entryHasKeyword(unit, entry, keyword, rule)` is the question "does it have it?". Pass the **rule of the army the entry belongs to**
(`getArchetypeRule(effectiveArchetypeFor(item, state))`); passing `null` silently turns every archetype grant off (that was #276).

### 5.3 Gating an Armory item — "who may buy this"

An `ArmoryItem` can carry several gates; **all are checked in `ArmoryModal.tsx` (`isAddBlocked` / `structuralReason`) and some in the validator**:

| Gate | Meaning |
|---|---|
| `requires_keywords` | the buyer has **any** of them (OR) |
| `requires_all_keywords` | the buyer has **all** of them (AND) ("Kroot infantry only") |
| `excludes_keywords` | the buyer has **none** ("units without the Flyer type") |
| `requires_unit_names` / `requires_owned_item` | role names ("Painboy only", incl. a promoted model) / another item already bought ("Exo-armor only") |
| `armour_compat`, `term_compat`, `gravis_compat` | armour-class compatibility (ᵀ, ᴳ glyphs) |
| mark glyphs (`ᴷ ᴺ ˢ`) and the mark armories | Mark of Chaos requirements; a model with every Mark (Black Crusade champion, Ascended Daemon Prince) passes all |
| `requires_army_item` | an item somewhere in the army (Inquisition Ordo) |
| Legacy-only items ("Vior'la Sept only") | `legacyItemAllowed` |

Most restrictions are **read from the item's own text at load time** (`textGates.ts`, `KEYWORD_SENTENCES`): "Kroot only", "Painboy only"… If a new
wording is not recognised, add it there rather than editing the item.

### 5.4 Archetypes, Legacies, Traits, Marks

* **Archetype** (`ArchetypeRule`, `src/engine/archetypes/base.ts`; the rules are in `archetypes/index.ts` and in each `codex_<faction>/archetypes`): a bag of
  flags — slot remaps, forced mark, allowed units/keywords, slot caps, `grantsKeywords`, allied faction grants… The sheet's *text* is shown to the player; the
  flag is what the engine acts on. A rule that is only text is not enforced.
* **Legacy**: gives access to an Armory (`armory_legions`) and sometimes more (a granted faction, a second Legacy). `effectiveLegacyFor` picks the one that
  applies to an entry.
* **Trait**: a unit-level effect. `traitEffects.ts` has the effect types: `stat_mod`, `inv_save`, `unit_ability`, `weapon_ability` (optionally `if_ability`),
  `weapon_range`, `grant_armory_item`, `grant_option_group`. "Select one improvement" traits (Cursed Founding…) choose from `TRAIT_SUB_EFFECTS`; the pick
  lives in `ArmyState.traitSubChoices`. **A trait that is only a sentence is shown but not applied** — list it as a gap, do not assume.
* **Marks** (`src/lib/markAccess.ts`, `markMods.ts`): who may take which Mark, what it gives (stat mods, Warded, Psyker for Tzeentch), which armories open.

### 5.5 Weapons: names, loadouts, counts

* A weapon with several firing modes is stored as several rows (`X - Mode` on the sheet-driven codices, `X (Mode)` in older data). Always compare through
  `src/utils/weaponName.ts` (`weaponBaseName`), never with `===` on names.
* The loadout is `equipped_with` text ("Every model is equipped with: …; The Exarch is equipped with: …"), parsed into clauses. Option groups then
  **grant** (`grantedQty`) and **replace** (`replacedQty`) weapons; the counts are derived from those, per model group.
* A promoted model (Sergeant/Exarch) either has its own row (built-in champion, or `variantArmoryActive` when its Armory purchases differ) or is folded into the
  squad's row. **Many bugs come from a model-specific effect landing on the squad's shared row** (an Exarch power marking every weapon). If an effect says "of
  the model", it belongs to that model's row, not to the shared one.

### 5.6 Engagements and the Missions

`src/engine/engagements.ts` holds the three battle types, their AOPs and their size **bands, which meet without gaps** (Skirmish 1000–1750, Pitched
1751–3500, Epic from 3501; a size typed in another band switches the type: `commitPointsLimit`). The Skirmish restrictions (stat caps, once-per-army upgrades,
unit-points caps, Squadrons) are in the `statCaps` section of `validators.ts` and follow `Codex/Custom40k Missions.docx`. **When the Missions change, diff
the text and update both the validator and the tests that encode the old rule.**

## 7. I want to change X → where

| I want to… | Look in |
|---|---|
| fix a unit's stats / points / weapons / option | the **sheet** (then "Run unit update"); never the unit JSON |
| fix an Armory item's price or text | the sheet; the Armory JSON follows it |
| change how an Armory item's text is understood (who may buy it, what stats it gives) | `data/textGates.ts` (who), `engine/equipMods.ts` (stats/abilities) |
| make an archetype do something new | `engine/archetypes/base.ts` (new flag) → use it in the engine → set it in `archetypes/index.ts` or `codex_<faction>/archetypes` |
| apply a trait effect to weapons or stats | `engine/traitEffects.ts` (effect type) + the faction's `codex_<faction>/traits.ts` |
| change what a weapon row shows (counts, rows, abilities) | `engine/resolver.ts` (`computeWeaponGroups`, `computeWeaponsToShow`), `engine/abilityMerge.ts` |
| change a legality rule | `engine/validators.ts` (and the UI gate, `ArmoryModal.tsx` / `UnitCard.tsx` / `SlotPanel.tsx`) |
| change slots or AOPs | `engine/archetypes/index.ts` (`getEffectiveSlotFor`), `engine/slotOverrides.ts`, `engine/validators.ts` (`getSlotUsage`, `getAopState`), `engine/engagements.ts` |
| change what the battle view shows | `lib/battleProfile.ts`, `components/PlayView.tsx` |
| change the printout | `components/PrintView.tsx` |
| add a UI string | `src/i18n/index.ts` (EN/DE/ES) **and** `ru.json`, `ja.json` — never an untranslated string in a component |
| add a rule description | `data/coreRules.ts` (kept by hand; follows the Core Rules text) |
| add a release note | `data/changelog.ts` (English) and, at release time only, the banner in `LandingPage.tsx` |

## 8. If I touch X → check Y

| If you touch… | …check |
|---|---|
| `resolveBase` / `computeWeaponGroups` / counts | the **whole-game snapshot** (§9): every faction changes together; guards `check_row_counts`, `check_sole_row_counts`, `check_weapon_swaps`, `check_weapon_grants` |
| a gate on Armory items | `ArmoryModal.tsx` and the validator both; the lower-case rule (§0.2); `check_armory_*` guards |
| keywords (`effectiveKeywords`, `grantedKeywords`) | traits in `store/army.ts` (`applyArmyTraits`), `resolver.ts` (`traitsApply`), `ArmoryModal.tsx` — all three read it |
| anything about "allied" | `isAlliedEntry`, `effectiveArchetypeFor`, `ownArmy`; `check_allied_*`, `check_ally_matrix_*` |
| slots / AOPs | `SlotPanel.tsx` and `validators.ts` must show the same numbers; `check_second_aop_*`, `check_free_slot_*`, `check_variant_hq_slot` |
| an option group's order or choices | saved lists (§3.2) |
| a Skirmish rule | `validators.ts` `statCaps` section; `check_skirmish_*` (they encode the Missions of the day) |
| `loaders.ts` normalisers | every faction (they run on all of them); `sanity_sweep` |
| stat maths (`equipMods`, `statPipeline`, `statMods`) | unit card, printout and TTS export all use them; the SV/BS/WS sign convention |
| `coreRules.ts` | the rule glossary shows text from here; check `lookupRule` for aliased names (`Lance` → `Armorbane`) |

## 9. How to verify a change

1. `npm run build` (type-checks the whole app). Run `npx eslint` on files you touched.
2. **Run the guards**: `npx tsx scripts/check_<topic>.ts` (see CONTRIBUTING "Guards — which one to run"). A guard encodes a rule someone once had to find out
   the hard way. If a guard fails because the rule changed on purpose (e.g. new Missions), **update the guard in the same change** and say so.
3. `npx tsx scripts/sanity_sweep.ts` — static checks over all the data (dead option groups, flag contradictions…). It has a known baseline of
   findings; a change should not add to it.
4. **Compare the whole game before and after** (`scripts/_snap_profiles.ts`): it dumps every unit's weapon rows alone and with each option taken.
   Run it on `main`, then on your branch, and `diff`. The only differences should be the ones you intended. Look at the multi-model units first: that is where
   a wrong count hides.
5. **Reproduce the report with the named units**, through the real path: build a `RosterEntry` and call `resolveUnitProfile` / `computeUnitPoints` /
   `validateArmy`; for the Armory, remember the modal compares **lower-case** keywords. "Cannot reproduce" almost always means the test used a different
   path than the app.
6. For something visible, look at it in the browser (`npm run dev`); for a rules text, compare with the canon in `Codex/`.

## 10. Pitfalls we have already paid for

| What happened | Why | How to avoid |
|---|---|---|
| Four Cataphractii weapons could not be bought (#292) | `isItemRequirementsBlocked` compares lower case; the bought armour keyword was added as "Cataphractii" | one function builds keyword lists |
| Legion units with a Mark got no Traits after a refactor (#276) | `entryHasKeyword(..., null)`: the archetype's rule was never passed | pass the rule of the entry's own army |
| A Chamber Militant army counted its main-list Inquisition units as allies | "allied" was tested as `factionSource === alliedFaction` in ~40 places | `isAlliedEntry` + `ownArmy` |
| "Poison(3+), Poison(3+)" on a weapon | several code paths add the same ability; the merge did not compare additions | `mergeWeaponAbilities` is the one place that resolves them |
| An Exarch's power marked every weapon of the squad; his claw showed "x5" | a model-specific effect on a shared row; a choice named with a profile mode did not match its weapon | think "which model's row?"; compare weapon names through `weaponBaseName` |
| Entourage freed no slot after a sheet update | the code looked for a "Herald:" line the sheet no longer prints | read numbers and names from the sheet's own text; do not hard-code a count |
| Daemonic possession improved BS/WS | BS/WS are stored in printed-number space (lower is better) | the sign convention in §4.1 |
| A 2+ save through Hardened Carapace passed Skirmish | the check read only the text of equipment, not the finished profile | check the resolved profile, which has every source |
| A fixed 1500-point cap blocked 2000-point lists | numbers written in the validator instead of `engagements.ts` | read limits from `ENGAGEMENTS` |
| A hand-fixed unit file reverted | unit files are regenerated | fix the sheet |

## 11. Process (short)

* One thing per PR. Say what you checked (§9) in the description, with the before/after if it touches the resolver.
* **Changelog** (`data/changelog.ts`) in English, one entry per version; **UI strings in five languages**; **docs**: a new file or a moved path means updating the
  five `CONTRIBUTING*.md` and the pointer in this file.
* **The maintainer decides versions, the banner and the push.** Do not bump `REVISION` / `ANNOUNCEMENT_KEY` or edit the banner in a PR.
  Banner convention: a bug that affects one faction goes in that faction's section; "Bugs (GitHub / Discord)" is for general bugs; "General" for changes and upgrades.
* Rules questions go to the rules author (Dominic); data errors go to the sheet owner. A comment on the issue saying *which* of the two it is saves everyone a round trip.
* If you are unsure what a change affects, ask — preferably with the file and the function name. This guide exists so that question is easier to answer.
