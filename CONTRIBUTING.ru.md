## Быстрый старт

```bash
git clone https://github.com/Rigzar/custom40k-builder.git
cd custom40k-builder
npm install
npm run build   # должна завершиться без ошибок
```

> **`scripts/` находится в `.gitignore`** — там лежат инструменты разработки мейнтейнера. Небольшой набор добавлен в репозиторий намеренно (`git add -f scripts/<имя>`): guard-проверки (`check_*.ts` / `.cjs`), инструменты для таблиц (`fetch_codex.cjs`, `unit_sync.cjs`, `check_unit_update.cjs`, `sync_codex_versions.cjs`, `convert_*.cjs`) и несколько тестов (`_gitfinda_test.mjs`, `_gitfinda_time_test.ts`, `_headers_test.ts`, `_ja_names_test.ts`, `_tts_*.ts`). Остальные скрипты, упомянутые в этом руководстве, есть только у мейнтейнера: попросите нужный в issue. TypeScript-скрипты запускаются так: `npx tsx scripts/<имя>.ts`.

> **Не запускайте `npm run dev`** во время работы — для проверки используйте `npm run build`. Приложение можно посмотреть, открыв `dist/index.html` после сборки, или на https://custom40k-builder.vercel.app.

## Сообщения о проблемах

Используйте GitHub Issues и выберите нужный шаблон:

- **Bug report** — что-то в приложении работает неправильно (неверные очки, не показывается опция, падение)
- **Data correction** — характеристики, оружие, опции или очки юнита не совпадают с правилами

Создавая issue, всегда указывайте:
- название фракции и юнита
- что вы ожидали и что получили
- если это проблема данных: страницу / раздел правил, на который вы ссылаетесь

## Исправления данных (без кода)

Это самый полезный способ помочь. Каждая фракция лежит в своей папке:

```
data/parsed/<фракция>/
  units/              <- один чистый .json на юнит (все фракции)
    troops/
      traitor_guard.json  <- один юнит: только JSON, без import/export
    hq/  elites/  ...      <- по папке на каждый слот
    index.ts           <- ЕДИНСТВЕННЫЙ .ts: импортирует все .json, экспортирует faction, slot_to_units, units
  unit-notes.md       <- (у некоторых фракций) старые комментарии из шапок, которые JSON хранить не может
  armory/
    general.json      <- общий арсенал (все модели)
    mark_khorne.json  <- арсенал по метке (фракции Хаоса)
    legion_*.json     <- арсенал ордена / наследия (по одному на наследие)
  archetypes.json     <- архетипы, наследия, черты
  animosity.json      <- таблица вражды меток / матрица союзников (только фракции с метками: CSM, CD)
  psychic/            <- дисциплины, молитвы, daemonkin
```

Два дополнения Horus Heresy устроены так же: `data/parsed/horus_heresy_legiones_astartes/` и
`data/parsed/horus_heresy_forces_of_the_machine_god/` (плюс `supplement.json` для арсенала и
частей, не связанных с юнитами). **Ключи фракций в приложении не всегда совпадают с названиями папок**
(`horus_heresy`, `legio_titanicus`): их сопоставляет только `src/data/loaders.ts`.

> **Все фракции используют один и тот же формат: чистый JSON.** Каждый юнит — файл `.json` без `import` и `export`,
> а в папке ровно ОДИН `.ts` — `units/index.ts`, который импортирует их все. Причина — инструментарий:
> помощник автора кодекса обновляет данные из таблиц автоматически и может делать это только с файлом, который
> на 100% является JSON. Чтобы изменить юнит, откройте его `.json`. В JSON нет комментариев, поэтому заметки из шапок
> старых `.ts`-файлов теперь лежат в `data/parsed/<фракция>/unit-notes.md` (Tyranids: `units/NOTES.md`). Чтобы ДОБАВИТЬ юнит,
> нужны ДВЕ вещи: его `.json`, а также один `import` и одна запись в `units` в `units/index.ts` (и его имя в нужном
> слоте в `slot_to_units`). `node scripts/convert_units_to_json.cjs <фракция>` конвертирует фракцию, которая
> всё ещё в старом формате (по умолчанию пробный запуск; `--lenient --write`, запускать через `npx tsx`, загружает и
> файлы, которые не являются буквальным JSON). Не запускайте конвертер и скрипты обновления на своих данных, не спросив.
>
> `node scripts/unit_sync.cjs "Codex/<фракция>.ods" <фракция>` сравнивает обновлённую таблицу с файлами юнитов и выводит все различия в очках, характеристиках и оружии (`--write` применяет их, `--equipped` также переписывает фразу «equipped with», если каждый предмет в ней — известное оружие). Он никогда не трогает группы опций и тексты способностей: их должен подключать человек.

### Кто пишет какое поле — и что делать, если таблица неверна

Файлы юнитов **написаны не целиком вручную**. Google-таблицы автора — источник истины для фактов
на датащите, а `UnwiseGetData/update_units.py` (см. *Автообновление юнитов* в конце) их переписывает. Разделение:

| Пишет обновление из таблиц (**не** править вручную) | Пишут люди (правьте свободно) |
|---|---|
| `name`, `models` (характеристики, очки, min/max), `variant_models`, `min_cost`, `default_size`, `equipped_with`, `weapons`, `abilities`, `unit_type`, `is_monster`, `keywords` | `option_groups`, флаги `has_armory_access` / `champion_has_armory` / `is_character` / `is_psyker` / `advisor`, `armory/`, `archetypes.json`, `psychic/`, правила движка |

**Если значение, которое пишет таблица, неверно — неверна ТАБЛИЦА: сообщите автору, не правьте JSON.** Ручную
правку перезапишет следующее обновление юнитов, а обходной путь в движке скрывает ошибку, которую автор
исправит одной ячейкой. Укажите точно вкладку и строку (*«Tau Hammerhead: у заголовка Railgun нет `*`»*)
и отправьте это в issue или в Discord. Примеры того, о чём сообщать: заголовок оружия без `*` (режимы не
связываются), имя, написанное двумя способами на одной вкладке (`Servoarm` / `Servo arm`), опция обмена,
называющая оружие, которого нет в таблице WEAPON юнита, ячейка с текстом, который относится к другому столбцу.
**Guard-проверки данных** (`check_*.ts`) — для *нашего* кода и *наших* полей; не учите их принимать ошибку таблицы.

Админские «исправления данных» (панель Inquisitor) типов очки, характеристика и оружие игнорируются для 19 фракций, которые
пишет скрипт (`applyDataOverrides(data, list, sheetOwned)`): там главнее таблица. Для дополнений Horus Heresy,
Legio Titanicus и Escalation они продолжают действовать.

### Добавление НОВОГО юнита

Юнит существует, только если он есть в **двух** местах. Имя, которое есть лишь в одном из них, недостижимо.

1. **`data/parsed/<фракция>/units/<слот>/<юнит>.json`** — сам датащит.
2. **`data/parsed/<фракция>/units/index.ts`** — **ДВЕ** записи, и именно этот шаг забывают:
   - строка `import dactylis from './heavy_support/dactylis.json';` и в карте `units`: `"Dactylis": dactylis as Unit,`
   - в `slot_to_units`, под нужным слотом: `"Dactylis",`

**Имя в `slot_to_units` без записи в карте `units` появляется в каталоге и ни к чему не разрешается.**
Орочий Lord of War так месяцами был недоступен.

**Имя должно совпадать ТОЧНО везде**, включая регистр: собственное `"name"` юнита, `"name"` каждой строки
модели, ключ в карте `units` и запись в `slot_to_units`. Движок ищет юнит именно по этой строке,
так что одна заглавная буква делает его другим юнитом.

**Сверяйте строку характеристик с заголовками столбцов.** В таблице идёт
`No. | NAME | M | WS | BS | S | T | W | I | A | LD | SV | POINTS`, и `T W I A LD` сливаются:
у Dactylis Wounds и Leadership оказались поменяны местами. `No.` — размер отряда, так что `1-2`
означает `min: 1, max: 2`.

**Оружие, помеченное `*` в таблице, имеет профили под собой**, и каждый — отдельная запись с именем
`"<Weapon> - <Profile>"`. Копируйте по одному профилю, строго по строке, и никогда не переносите список
способностей одного профиля на другой: два профиля пришли со способностями соседа и поэтому вообще
остались без `AT(2)`. Способность с незакрытой скобкой (`Suppression(3`) не разрешается ни во что,
потому что поиск идёт по точному тексту.

**Не копируйте «may select any number of Basic and Advanced Biomorphs (see Armory)»** и любую
подобную строку в опции юнита. Это живёт в арсенале фракции, и приложение добавляет их само.
В `option_groups` попадают только опции, которые называет сам датащит, с их собственными ценами.

**Проверка без Node:** прочитайте свой файл рядом с таблицей поле за полем, затем откройте вкладку
«Files changed» в PR и убедитесь, что все три файла выше на месте. Если `units/index.ts` нет в
списке, юнит не подключён. Напишите об этом в PR, если хотите, чтобы его прогнали через сравнение
с кодексом до слияния — этот инструмент выводит по строке на каждое поле, не совпадающее с таблицей.


### Порядок работы

1. Откройте `data/parsed/<фракция>/units/<слот>/` и нужный `.json`-файл.
2. Объект использует названия полей из таблицы ниже. В JSON нет комментариев: если юниту нужна заметка, положите её в `unit-notes.md` рядом с `units/`.
3. Сверьте каждое поле со своей копией правил.
4. Исправьте ошибки, затем запустите `npm run build`, чтобы убедиться, что JSON корректен и приложение собирается.
5. Откройте Pull Request.

### Поля, которые нужно проверить у юнита

Поля из столбца «пишет таблица» выше показаны здесь, чтобы вы знали, на что смотреть при проверке таблицы;
сообщайте о расхождениях, не правьте их. `option_groups`, флаги, `armory/` и `archetypes.json` исправляете вы.

| Поле | Что проверить |
|---|---|
| `models[].points` | Стоимость модели в очках |
| `models[].min` / `models[].max` | Минимальное и максимальное число моделей |
| `models[].stats` | M / WS / BS / S / T / W / A / Ld / Save |
| `weapons[]` | Присутствуют все профили оружия; верные S / AP / D / Abilities |
| `option_groups[]` | Текст заголовка совпадает с правилами; перечислены все варианты; верные цены |
| `option_groups[].per_model` | Ставьте `true`, когда в заголовке «for +X points **per model**» или «the entire squad may receive one of the following... **per model**» — относится и к inline-опциям (`inline_pts`), и к обычным группам `choices[]`; без этого цена берётся один раз за весь юнит и не растёт с размером отряда |
| `option_groups[].replaces` | Перечислите точные названия оружия, которое убирает этот обмен. Обязательно для любой группы, которая должна убирать старое оружие из таблицы оружия — без этого показываются и старое, и новое. Для оружия с несколькими профилями (например «Taser lance - Charge» / «Taser lance - Melee») перечисляйте каждое имя профиля, а не общий префикс — сопоставление идёт по точному имени. **Ловушка**: название варианта, точно совпадающее с названием безусловно показываемого базового оружия, по умолчанию скроет это оружие — никогда не давайте чисто добавляющему варианту (даёт БОЛЬШЕ оружия, уже входящего в `equipped_with`) то же самое имя, что у базового оружия. |
| `option_groups[].choices[].name` (с числом впереди) | **Никогда** не называйте вариант «two X» / «2 X» / «four X» и т. п. — привязка к таблице оружия сопоставляет название варианта с названием оружия точно, поэтому число впереди никогда не совпадёт, и оружие показывается всегда, даже некупленное. Переименуйте вариант в голое название оружия в единственном числе (заголовок уже передаёт «both»/«two»/и т. д.); цена не меняется. |
| `is_character` / `is_vehicle` / `is_psyker` | Флаги классификации юнита |
| `champion_has_armory` | True только если чемпион (аналог сержанта) имеет доступ к арсеналу независимо |
| `advisor` | True только для юнитов-советников (например, Commissar) |
| `abilities[]` | Текст способности есть и верен |
| `unit_type` | Должен быть в каноническом написании из Core Rules: `Infantry`, `Bike`, `Character Model`, `Jet Bike`, `Jump Pack Infantry`, `Monstrous Creature`, `Monstrous Infantry`, `Walker`, `Flyer`, `Vehicle` |

### Типы ограничений для `option_groups`

| `constraint.type` | Значение |
|---|---|
| `one` | Выбрать 0 или 1 из списка (самое частое) |
| `every` | Каждая модель выбирает независимо — стоимость за модель |
| `per_n` | M выборов на каждые N моделей (`constraint.per_n` задаёт N, `constraint.count_per_n` — M; например «for every 3 models, 1 may swap» — это `per_n:3, count_per_n:1`) |
| `fixed_max` | До N выборов всего (`constraint.max` задаёт N) |
| `fixed_max` + `reduced_when_selected` | Потолок снижается до меньшего `max`, когда в другой группе (`if_group`, по индексу) есть выбор — например Warbuggy: 3 малых орудия, но 1, если взято большое |
| `per_n` в группе без вариантов и с `inline_pts` | Считаемая галочка: степпер до числа блоков по N моделей, цена за каждый — например один Vox на каждую Heavy Weapons Team |
| `mark` | Выбор метки Хаоса |
| `veteran` | Слот ветеранской способности |
| `unique_upgrade` | Ограничение уникальности на уровне юнита |

Два флага самой группы, не типы ограничений: `per_model: true` (стоимость растёт с отрядом) и
`independent_choices: true` (у каждого варианта свой лимит вместо общего пула — списки биоморфов
Tyranids, где старый общий `max: 16` был ЧИСЛОМ ОПЦИЙ, а не правилом).
`variant_link` связывает группу с повышением в `variant_models` (Spanna, Overlord, Veteran Sergeant);
`applies_to_model` ограничивает обмен одной строкой модели. **Новые варианты добавляйте В КОНЕЦ списка**: сохранённая
армия хранит ИНДЕКС варианта, так что перестановка молча сдвигает чужой выбор.

### Добавление оружия, предмета арсенала, архетипа, черты или наследия

**Сначала нужно понять одно: записать правило — не значит, что оно что-то делает.** Большинство из
них живёт в ДВУХ местах — в ДАННЫХ, благодаря которым оно появляется и оценивается, и в ДВИЖКЕ, благодаря
которому оно действует. Проверка всех записанных правил фракций нашла 56, которые ничто в приложении
никогда не читало. Многие были только таблицами и правильно оставались текстом, но четыре оказались
настоящими багами: реликвия, ничего не дававшая; ward save, которого не получили 13 датащитов; улучшение
для всей армии, оказавшееся бесплатным, и условие, бывшее украшением.

`node scripts/audit_faction_rule_coverage.cjs <фракция>` перечисляет правила, на которые движок не может влиять.

**Оружие на датащите** идёт в `weapons[]` этого юнита. Если в таблице оно помечено `*`, каждый профиль
— отдельная запись с именем `"<Weapon> - <Profile>"`. Если опция ЗАМЕНЯЕТ оружие, группе опций
нужен `replaces` с точными названиями оружия, каждый профиль расписан — без этого показываются и старое,
и новое. Никогда не ставьте число в название варианта («two Flamers»): привязка сопоставляет название
варианта с названием оружия точно, и тогда оружие показывается, куплено оно или нет.

**Предмет арсенала** идёт в `armory/general.json` (или `mark_*.json` / `legion_*.json`). Копируйте
столбцы цен как в таблице — это NORMAL / CHARACTER MODELS / MONSTROUS CREATURES &
VEHICLES, а третий — для Monstrous **Creatures** и техники, не для Monstrous Infantry. Копируйте
описание дословно: движок его читает. `Unique` с заглавной U означает «один раз на армию»;
«can be taken multiple times» и «every enhancement is unique per army» читаются из этого же
текста. Предмет, в тексте которого способность взята в двойные кавычки, автоматически даёт эту способность —
поэтому формулировка важнее, чем кажется.

**Архетип** — это запись в `archetypes.json` И правило в
`src/engine/archetypes/index.ts` (`ARCHETYPE_RULES`). Один JSON делает его выбираемым и ничего
больше. Его `notes` показываются игроку и ничего не дают; всё, что должно реально
происходить — перенос слота, лимит, выданная способность — это поле объекта правила. Три архетипа
Inquisition всё ещё не разрешаются ни в какое правило, так что приложение их предлагает, а они ничего не делают.

**Черта** — это запись в `archetypes.json` И эффекты в `traits.ts` этой фракции
(`TRAIT_EFFECTS`). Три столбца цен совпадают со столбцами арсенала, а `*` означает, что цена
за Wound или Hull point. Каждый эффект несёт `applies_to` — `all`, `creature`, `vehicle`, `character`,
`infantry`, `monster` или `psyker` — и эта область определяет, кто его получает. Черта без записи в
`TRAIT_EFFECTS` выбирается, стоит очков и ничего не меняет.

**Наследие** — запись в `archetypes.json`, чей `armory_key` **должен совпадать** с ключом, используемым для
этой фракции в `src/data/loaders.ts`; если они расходятся, вкладка арсенала не появится. Если
фракция держит все реликвии наследий в одном файле, текст каждой реликвии несёт своё ограничение
(«Alaitoc only.», «Ymyr Conglomerate only.»), а условие выводится из описания самого наследия —
поэтому оба предложения нужно копировать точно как написано.

**Целая фракция** — это не просто выгрузка данных: ей нужны своя папка, запись загрузчика в
`src/data/loaders.ts` и строка и столбец в матрице союзников в `src/data/alliedMatrix.ts`.
Откройте issue, прежде чем начинать.

### Структура файлов арсенала

`armory/general.json` содержит оружие, снаряжение и оружие демонов, доступные всем подходящим моделям. Арсеналы меток (`armory/mark_khorne.json` и т. д.) и арсеналы орденов/наследий (`armory/legion_*.json`) устроены так же:

```json
{
  "name": "Armory Name",
  "weapons": [...],
  "equipment": [...],
  "daemon_weapons": []
}
```

Поле `armory_key` в каждой записи наследия в `archetypes.json` **должно совпадать** с ключом, используемым в `src/data/loaders.ts` для объекта `armory_legions` этой фракции — если они расходятся, вкладка арсенала наследия не появится. История — в `ki-legacy-armory-link-01`.

> **Русский (RU) и японский (JA) появились в октябре 2026 года.** В приложении и вики теперь пять языков: EN, DE, ES, RU, JA.

> - **Баннер, шпаргалки, карточки дополнений, окно журнала изменений, сообщения:** у каждого своя таблица по языкам в своём компоненте; добавьте блок `ru`/`ja` рядом с `es`.
> - **Вики:** `wiki/src/lib/i18n-builtin.ts` (интерфейс + главная) по языкам; `npm run build` в `wiki/` собирает все языки в один `dist/` (английский в корне, остальные в `/de`, `/es`, `/ru`, `/ja`). Длинные страницы Core Rules и Missions переводятся блок за блоком из собранного английского HTML (`wiki/scripts/extract-page-strings.mjs` → `wiki/src/data/page-strings/`, переводы в `wiki/src/data/page-translations/<язык>.json`); после правки этих английских страниц запустите экстрактор заново и добавьте новые строки. Тексты способностей датащитов лежат в `src/data/abilityTexts.<язык>.json` (по `abilityKey`), а последние записи журнала изменений — в `src/data/changelog.i18n.json`.
> - Админ-панель Inquisitor остаётся английской; её редактор переводов охватывает все четыре неанглийских языка.

Приложение поддерживает пять языков: **английский (EN)**, **немецкий (DE)**, **испанский (ES)**, **русский (RU)** и **японский (JA)**. EN, DE и ES находятся в `src/i18n/index.ts`; RU и JA — в `src/i18n/ru.json` и `ja.json` (см. примечание выше). Переводимый текст живёт в нескольких разных местах — прочитайте разделы ниже, прежде чем начинать.

### 1. Строки интерфейса — `src/i18n/index.ts`

Здесь лежат все подписи интерфейса, тексты кнопок и заголовки разделов. В `index.ts` таблица — по одному объекту на язык (`en`, `de`, `es`), в каждом одни и те же ключи:

```ts
// en: { ... appTitle: 'Custom 40k Army Builder', ... }
// de: { ... appTitle: 'Custom 40k Armeeliste', ... }
// es: { ... appTitle: 'Creador de Ejércitos Custom 40k', ... }
```
RU и JA — плоские JSON-файлы с теми же именами ключей. Ключ, отсутствующий в языке, откатывается на английский; **новый ключ нужно добавить в объединение `TranslationKey` в `index.ts` и во все пять таблиц**.

**Как найти непереведённые строки интерфейса:**
Найдите в файле (и в `ru.json` / `ja.json`) записи, где значение совпадает с английским — это машинный перевод или пропуск. Правки носителей языка всегда приветствуются.

**Добавление или исправление перевода интерфейса:**
1. Откройте `src/i18n/index.ts`.
2. Найдите строку (ищите английский текст).
3. Измените значение `de` / `es` (или строку в `ru.json` / `ja.json`).
4. Запустите `npm run build` — файл на TypeScript, поэтому опечатка вызовет ошибку сборки.
5. Откройте Pull Request. Исправлять каждую строку не обязательно — частичные улучшения приветствуются.

> **Немецкая терминология:** используйте официальную немецкую терминологию Games Workshop, а не дословные переводы. Названия слотов следуют конвенции GW: `Standard` (Troops), `Elite` (Elites), `Sturm` (Fast Attack), `Unterstützung` (Heavy Support). Сокращения характеристик: `Reichw.` (Range), `DS` (AP), `SW` (Damage). Арсенал — `Rüstkammer`.

### 2. Описания правил — журнал изменений, известные проблемы и файлы движка

Текст правил в движке (описания черт, заметки архетипов, описания способностей) сейчас **только на английском**. Он хранится обычными строками в TypeScript-файлах движка и в `src/data/changelog.ts` / `src/data/known-issues.ts`.

**Чем канонический шаблон комментариев помогает переводчикам:**
В каждом файле движка (архетипы, черты, наследия) исходный текст правила лежит комментарием прямо над кодом, который его реализует, например:

```ts
// SOURCE: CSM Army Customisation — Traits
// Blood Feud: If the unit uses a Charge order or gets charged by an enemy
// unit, it gains +1 to melee hit rolls until the end of the current battle
// round. COST: 5 normal · 0 character · 5 monster/vehicle
'Blood Feud': [
  { type: 'unit_ability', name: 'Blood Feud', desc: '...', applies_to: 'all' },
],
```

Комментарий даёт точный английский исходный текст, так что вы знаете, что именно должно говорить `desc` по-немецки или по-испански. Открывать исходные HTML-файлы не нужно.

**Как перевести описание правила — сделать поле многоязычным:**

Поля `desc` правил сейчас — простые английские строки. Чтобы сделать поле многоязычным, измените его тип со `string` на `I18nString` (определён в `src/data/changelog.ts`):

```ts
// До — только английский:
desc: 'The unit gains +1 to melee hit rolls when charging or charged.',

// После — три языка:
desc: {
  en: 'The unit gains +1 to melee hit rolls when charging or charged.',
  de: 'Die Einheit erhält +1 auf Nahkampf-Trefferproben, wenn sie angreift oder angegriffen wird.',
  es: 'La unidad gana +1 a las tiradas de golpe en cuerpo a cuerpo al cargar o ser cargada.',
},
```

Хук `useT()` в интерфейсе сам разрешает `I18nString` в активный язык — менять интерфейс не нужно, только данные. Когда вы смените тип, TypeScript подскажет, где обновить каждое место, читающее это поле.

**Шаги для преобразования поля desc:**
1. Измените тип поля в `types/data.ts` или нужном интерфейсе со `string` на `I18nString` (импорт из `'../data/changelog'`).
2. Обновите значение в файле движка до объектной формы `{ en, de, es }`.
3. Запустите `npm run build` — TypeScript отметит все оставшиеся использования этого поля как простой строки, так что вы ничего не упустите.
4. Если пока есть только английский перевод, можно использовать тот же текст для всех трёх как заглушку: `{ en: '...', de: '...', es: '...' }` — носитель языка потом улучшит DE/ES.

**Журнал изменений и известные проблемы** (`src/data/changelog.ts`, `src/data/known-issues.ts`) уже используют `I18nString`. Журнал изменений пишется по-английски в `changelog.ts`; немецкие, испанские, русские и японские версии новейших записей лежат в `src/data/changelog.i18n.json` по версиям, и **в массиве каждого языка должно быть ровно столько пунктов, сколько в английской записи, иначе перевод молча игнорируется** (проверяет `scripts/_changelog_align_test.ts`). Добавляйте английский пункт и четыре перевода в одном изменении. У объявления на главной (`ANNOUNCEMENT_TEXT` в `LandingPage.tsx`) тоже есть блок на каждый язык: добавляйте ту же строку во все пять.

### Pull request с переводами

- Для PR, затрагивающих только `i18n/index.ts`, полная среда разработки не нужна. Измените файл, запустите `npm run build`, убедитесь, что он проходит.
- Если не уверены в переводе, оставьте заметку в описании PR.
- Машинный перевод допустим как отправная точка; проверка носителем языка предпочтительна.

### Навигация — четыре шага

Сборка армии — линейный поток из четырёх шагов, а не набор вкладок. `App.tsx` хранит всё
состояние навигации: `screen` (`'home'` | `'flow'`), `step` и `detachment` (какую армию показывает шаг
Units). Больше ничто в приложении не решает, где находится игрок — если вы собираетесь
добавить вторую машину состояний внутри компонента экрана, это та самая ошибка, которую заменили.

| Файл | Ответственность |
|---|---|
| `components/StepBar.tsx` | Сама панель шагов + тип `Step` и `STEP_ORDER`. Шаги ②-④ заблокированы, пока не загрузятся данные фракции. На телефоне подпись остаётся только у активного шага. |
| `components/LandingPage.tsx` | ТОЛЬКО парадный вход — логотип, заметки о релизе, объявление админа, быстрая загрузка, дополнения. Здесь не должно появляться собственных экранов. |
| `components/FactionStep.tsx` | ① Battle Setup + сохранённые армии + сетка фракций. |
| `components/ReviewStep.tsx` | ④ Вердикт, очки (по отрядам-детачментам), полный список валидации, сохранение/печать/экспорт. |
| `data/factionCatalog.ts` | `CATEGORIES` / `ALL_FACTIONS` / `DEFAULT_CODEX_VERSIONS` — простые данные, общие для сетки фракций и админ-панели. |

Шаги ② (Configuration) и ③ (Units) отрисовываются прямо в `App.tsx`. ② отвечает за всё в
армии, что не является юнитом: доктрину, наследие, черты и союзный детачмент. ③ отвечает за
каталог и список, с переключателем Primary / Allied, когда есть союзник.

**Правила для всего, что вы сюда добавляете:** переход между шагами никогда не должен терять данные — единственное
исключение — смена фракции при юнитах на столе, и тогда спрашивается подтверждение. У любого
экрана, до которого может добраться игрок, должен быть видимый выход, не уничтожающий его работу.

### Названия оружия и режимы стрельбы (`src/utils/weaponName.ts`)

Оружие с несколькими профилями хранится как одна запись на режим, и в данных **два написания**:

```
Plasma pistol - Standard   /  Plasma pistol - Overcharged     (дефис)
Plasma gun (Standard)      /  Plasma gun (Overheating)        (скобки)
```

`resolver.ts`, `PrintView.tsx` и `UnitCard.tsx` каждый делили строку только по `' - '`, так что всё
оружие со скобками для приложения было тремя разными видами оружия — режимы
печатались отдельными строками, и только у одного было верное количество. Всегда используйте
`weaponBaseName` / `weaponMode` / `isModeRow` из этого файла; никогда не переписывайте деление заново.

**Это только для названий ОРУЖИЯ.** Отбрасывать конечное `(...)` там безопасно — ни у одного оружия в
игре нет скобок в конце, если это не режим, — но для названий вариантов опций это *небезопасно*: у Orks есть
вариант, оканчивающийся на `(counts as two arm weapons)`.

**Сопоставление варианта обмена со строкой оружия** (`weaponKey`, `resolveChoiceWeapons` в том же файле): варианты
опций пишут люди, а строки оружия — таблица, поэтому `Big Zzappa` / `Big zzappa` или `Two Grot bomms` /
`Grot bomm` всё равно должны находить друг друга. Помощник пробует точное имя, затем многопрофильные строки `"X - "`, затем
нестрогий ключ (регистр, число впереди и множественное `s` игнорируются), затем составные имена (`A & B`). Используйте его везде, где
название варианта ищется в `weapons[]`; никогда не сравнивайте две строки сами.
`scripts/check_choice_weapons_match.ts` это закрепляет.

### Количества в каждой строке (`src/engine/resolver.ts`)

Каждая строка модели и каждая строка оружия показывает своё количество, **даже если оно равно 1** (`1x Overlord`, `9x Marine +
1x Sergeant`, `3x Spanna`). Их несут два поля:

- `modelRowCounts[i]` — всегда число, параллельно `modelsToShow`. **Это то, что печатают карточка, версия для печати
  (оба макета) и Battle View.** У повышенной модели своё количество (`variantCount`); отряд
  с одной масштабируемой строкой модели измеряется через `item.size`; иначе собственная строка отряда берёт то, что
  оставляют фиксированные модели.
- `weaponGroups[].count` и `countOverrides` — префикс «Nx» у оружия. `fillMissingWeaponCounts` заполняет любую
  группу без количества моделями, которые её несут (умноженными на число копий, которое даёт каждой `equipped_with`).

`modelCounts` (может быть null) по-прежнему существует и **означает другое**: «эта строка отделена
повышением». Арифметика оружия читает там null как «не отделена», так что не печатайте его.
Отряд с единственной масштабируемой строкой модели (Lootas, Burna Boyz, Dire Avengers…) должен считать оружие по
`item.size`, а не по минимуму модели — у Lootas при 15 моделях было `5x Deffgun`, пока это не исправили.

```
npx tsx scripts/check_row_counts.ts        # строки моделей и группы оружия никогда без количества
npx tsx scripts/check_sole_row_counts.ts   # случай Lootas, с Spannas и без
```

**Перед изменением общей арифметики сделайте снимок.** `scripts/_snap_profiles.ts` печатает группы оружия каждого юнита
с каждой опцией по отдельности; `SNAPMAX=1` делает то же при максимальном размере отряда. Сравните вывод
до и после. Проверка только затронутого юнита скрывает регрессии в остальных сорока.

### Окно арсенала (`src/components/ArmoryModal.tsx`)

- **Количества, а не галочки.** Предмет, который можно купить несколько раз, — степпер `[-] n/max [+]`
  (`CopyStepper`); единый лимит — `copyCap`, он передаётся через `ArmoryCountsContext`. Полоса сверху, «Что
  вы несёте», перечисляет каждую покупку с ✕, итог, ветеранские слоты `n/max` и «Убрать всё».
- **Серая строка объясняет почему** (`blockReason`: лимит достигнут, уникально на армию, слот Kustom job занят, конфликт
  брони, «Only for Mek», нет цены, ветеранские слоты заполнены). Добавляйте причину рядом с правилом, которое блокирует
  строку, с ключом на всех пяти языках.
- **Техника и юниты разделяются по `category`** (`vehicle`, `veteran`, без неё). Техника, не являющаяся персонажем,
  видит только снаряжение техники (и Kustom jobs орков); не расширяйте это, не проверив таблицу.
- **Блок повышения не повторяет кнопку арсенала**, когда у юнита уже есть доступ на весь юнит
  (`has_armory_access`): у Necron Lord казалось, что титул Overlord его открывает. Блок появляется только при доступе
  одного чемпиона.
- **Профили оружия без цены** в таблице WEAPON арсенала — это оружие, которое дают улучшения техники или оружие
  демонов; они показываются серыми как «нет цены». Это раскладка таблицы, а не баг, который нужно латать.

### Переименованные и удалённые датащиты (`src/engine/unitRenames.ts`)

Сохранённая армия хранит каждую запись по **ИМЕНИ** юнита. Когда автор переименовывает или удаляет датащит,
это имя перестаёт разрешаться — а каждый потребитель в приложении одинаково обращается с неразрешимым юнитом:
`resolveUnit()` возвращает `undefined`, `UnitCard` возвращает `null`, а сумма очков берёт `: 0`. Результат —
худший вид сбоя: запись отображает **ничего**, стоит **ничего** и всё ещё
занимает слот. Игрок видит заголовок слота «*1 unit · 0 pts*» без карточки под ним и
армию, которая тихо подешевела.

Поэтому обновление кодекса, которое переименовывает или удаляет юнит, требует одного из двух:

- **Переименован** → добавьте в `RENAMED_UNITS` (по отображаемому названию фракции). Он переносится вперёд при
  загрузке, и в `importRoster`, и в миграции persist, так что игрок ничего не замечает. Храните записи
  вечно; удаление одной ломает чей-то сохранённый список.
- **Удалён** → добавьте короткую заметку в `REMOVED_UNITS`. Это только улучшает сообщение. Обнаружение
  **не** зависит от таблицы: валидатор помечает любую запись, которая не разрешается, а `ArmyList`
  рисует вместо неё `MissingUnitCard` с кнопкой Remove.

- **ГРУППА опций, которую обновление удаляет** → добавьте её индекс по СТАРОЙ нумерации в
  `REMOVED_OPTION_GROUPS`. `optionQty` индексируется `[groupIndex][choiceIndex]`, поэтому удаление группы
  перенумеровывает все следующие, и выбор в сохранённом списке съезжает на не те опции.
  `applyOptionGroupRemovals()` убирает удалённые ключи и сдвигает оставшиеся вниз при загрузке, рядом
  с двумя переименованиями выше. Рабочий пример — Space Marines 1.04: обмен Krak missile launcher у Desolation Squad
  исчез, потому что Krak missile стал бесплатным вторым профилем
  стандартной пусковой, что превратило бы каждое сохранённое улучшение Veteran Sergeant в Vengor
  launcher. Добавление нового *варианта* не требует миграции, пока он идёт В КОНЕЦ списка.

У архетипов та же проблема и то же решение этажом выше — `RENAMED_ARCHETYPES` в
`src/engine/archetypes/index.ts`.

### Обмен оружия (`scripts/check_weapon_swaps.ts`)

Группа опций с `replaces: ["X"]` заставляет движок убрать X, когда обмен куплен.
Без неё новое оружие просто **добавляется**, карточка показывает оба, и в отряде оказывается больше
стволов, чем моделей. Ничего не падает, очки остаются верными — неверен только список оружия.

```
npx jiti scripts/check_weapon_swaps.ts
```

Он помечает любую группу, в заголовке которой есть слова swap/replace/exchange, которая называет оружие
юнита, предлагает варианты и не имеет `replaces`. **Завершается с ненулевым кодом**, поэтому его безопасно ставить
в проверку перед push. GH#116 был одним из таких случаев, а проверка, которую он вызвал, нашла ещё 26 в 9 фракциях.

Две формы, на которые нужно смотреть в заголовке, прежде чем действовать:

- **Отдаётся только одно оружие, даже когда названо два.** Inquisition Servitors: *«swap their
  Paired shock chargers **for a** Shock charger and...»* — Shock charger вы получаете.
- **Цепочки обменов заменяют ПРЕДЫДУЩЕЕ оружие, а не базовую экипировку.** Termagant оснащён
  Spinefists; группа 1 меняет их на Fleshborer; группа 2 затем меняет *Fleshborer*.

### Снаряжение, называющее оружие (`scripts/check_weapon_grants.ts`)

Предмет арсенала выдаёт оружие одним из двух способов: структурированным `effect.grants_weapons` или
разбором текста, который узнаёт несколько форм предложений. Из разбора легко выпасть, и тогда
игрок молча ничего не получает:

```
"...+1 Wound, a twin shuriken catapult and the ability "Jet bike"."   составное предложение
"Additionally, it gains the "Cleansing flame" weapon."               не "the model gains"
"The model gains a Twin heavy stubber."                              "stubber" — неизвестный суффикс
```

Это были 13 предметов в 9 фракциях (GH#119). Проверка работает в обратную сторону — она берёт
**настоящие названия оружия** фракции и ищет их в описаниях предметов, и ей всё равно, как
сформулировано предложение.

```
npx jiti scripts/check_weapon_grants.ts
```

**Две вещи, которые нужно знать, прежде чем действовать по срабатыванию.** Это список для проверки, а не вердикт:
описание может законно упоминать оружие, чтобы его УСИЛИТЬ («the Immolator's Twin heavy flamer gains +1
Strength»). И `effect.grants_weapons` разрешается **только** по `armory_general.weapons`, так что
название оружия, которого нет в этом списке, ничего не даёт — сначала добавьте его туда как запись
«только выдаваемое» (обе цены `null`, соглашение «Ossific Blades»). Проверка помечает и этот случай.

### Формы данных фракций (`scripts/check_faction_shapes.ts`)

`loaders.ts` собирает каждую фракцию из ~20 динамических импортов JSON и возвращает результат
как `as unknown as FactionData`. Это приведение несёт нагрузку, но из-за него **поле может иметь неверную
форму во время выполнения, а компилятор всё равно сочтёт его допустимым**.

Это не теория. `pacts` по умолчанию было `{}` у 18 фракций без `pacts.json`, а его тип обещал `Power[]`,
поэтому `data.pacts.find(...)` падал с `find is not a function` и обрушивал
всю версию для печати для любой армии с выбранной психосилой — неделями, молча (GH#113).

```
npx jiti scripts/check_faction_shapes.ts
```

Он проводит все 21 фракцию через настоящий загрузчик и проверяет, что всё, на чём код вызывает
`.find()` — `prayers`, `pacts`, каждая дисциплина, каждый раздел арсенала — действительно массив.
**Запускайте после правок `loaders.ts`, любого файла данных `psychic/` или `armory/` либо типа `FactionData`.**
Завершается с ненулевым кодом на первой же проблеме.

### Правило фракции ПОДКЛЮЧЕНО или только записано? (`scripts/audit_faction_rule_coverage.cjs`)

Каждый `codex_<faction>/special-abilities.ts` хранит правила фракции дословно. Проверка спрашивает про
каждое: встречается ли его ИМЯ там, где движок мог бы НА НЕГО ДЕЙСТВОВАТЬ? Документация
(`special-abilities.ts`, `keywords.ts`, `src/data/`, справки rules-model) не считается.

```
node scripts/audit_faction_rule_coverage.cjs            # сводка по фракциям
node scripts/audit_faction_rule_coverage.cjs --list     # каждое правило, существующее только текстом
node scripts/audit_faction_rule_coverage.cjs necrons    # одна фракция
```

**Упоминание ничего не доказывает. ОТСУТСТВИЕ упоминания доказывает, что правило не может сработать** — только
в эту сторону проверке можно верить. Она появилась, потому что игрок нашёл Eldar *Webway strike*, верно
задокументированный, верно напечатанный и ни к чему не подключённый; ни один аудит данных этого не видел, потому что данные
были верны.

**Вывод — это рабочий список для ЧТЕНИЯ, а не список багов.** Большинство записей — действия за столом и правильно
остаются текстом. Важная категория — `army-rule`.

Из первого прохода получились две guard-проверки, обе стоит копировать по форме:

- `check_weapon_grants_unit_ability.ts` — «если одна модель оснащена X, отряд получает Y».
  **«Equipped with» означает выданное или взятое опцией, а НЕ напечатанное на датащите**; каждое
  покупаемое оружие напечатано, так что нестрогое прочтение неверно на 11 из 12 листов Grey Knights.
- `check_named_ward_abilities.ts` — способность, КОТОРАЯ является ward save, но не называет число
  (Sororitas *Shield of Faith*, 6+, определена только в Index). **Лучшее значение всё равно должно побеждать**,
  так что 6+ никогда не перезаписывает лучший сейв, а `Aegis(X+)` должна оставаться неразобранной — это бросок на рассеивание.

### Улучшения реликвий (`scripts/check_enhancement_uniqueness.ts`)

Девятнадцать реликвий позволяют улучшить одно оружие одним из +6″ дальности / +1 силы / -1 AP / +1 AT.
Десять из них также говорят **«Can be taken multiple times»**, а все девятнадцать говорят, что улучшение
**уникально на армию**.

```
npx tsx scripts/check_enhancement_uniqueness.ts
```

**У строки об уникальности ДВЕ формулировки.** Восемнадцать говорят «Every **enhancement** is unique per army»;
Adeptus Custodes *Vault weapon* говорит «Each **improvement** is unique per army». Если искать только
первую, правило этой реликвии молча не выполняется — `enhancementsUniquePerArmy()` принимает обе.

**Реликвии, которую можно брать несколько раз, нужны ОБА выбора открытыми**, а не только
выбор улучшения: вторая копия тоже должна сказать, какое оружие улучшает. Guard называет каждое условие
отдельно, и это сделано намеренно — ранняя версия искала общий помощник и проходила,
пока условие улучшения было сломано, потому что условие выбора оружия строкой выше совпадало с
ним. Это поймали, прогнав настоящее окно, а не проверкой.

**Правило проверяется дважды намеренно**: выбор затеняет уже взятое, а
валидатор помечает дубликаты — список, сохранённый до исправления, содержит такой, и никакой выбор не может
пометить его задним числом.

### Правила развёртывания, покупаемые за Wound (`scripts/check_deployment_upgrades.ts`)

Пять фракций продают на вкладке Index правило, позволяющее выставить один юнит иначе, с оплатой за
Wound: Eldar/Harlequins **Webway strike**, Dark Eldar **Webway raid** (Infiltrators, +1/Wound,
пехота), Custodes **Lightning strike** (Deep Strike, +1/Wound или +4/Hull Point, Infantry/Walker)
и Orks **Tellyporta** (Deep Strike, +1/Wound, +4/Hull Point для техники и monstrous creatures).
Они находятся в `src/engine/deploymentUpgrades.ts` и переключаются для каждой записи ростера.

```
npx tsx scripts/check_deployment_upgrades.ts
```

**«For each STARTED 1000 points» означает CEIL**, как и орочье «or part thereof» — лимит
проверяется на 1000 *и* 1001 именно потому, что в этой кодовой базе уже путали пару floor/ceil
(«for every 500 points» — это floor).

**`computeUnitPoints` принимает `faction` как ОБЯЗАТЕЛЬНЫЙ параметр и должен продолжать это делать.** Значение
по умолчанию позволило бы забытому месту вызова молча недоначислять; сейчас, пока параметр обязателен, компилятор называет все
двенадцать. Передавайте `factionForEntry(item, data)`, а не `data.faction` — союзная запись оценивается по
фракции СОЮЗНИКА, потому что союзный детачмент выбирает собственный Army Customisation.

**`resolveUnit` в `points.ts` — это ПОИСК юнита, а не вызов расчёта цены.** Его модели несут
базовую цену датащита и никогда не меняются, так что проверка изменения цены через него всегда даёт ноль. Считайте цену
через `computeUnitPoints` или через `pts` резолвера.

### «Objective secured!» и союзные детачменты (`scripts/check_objective_secured_allies.ts`)

Core Rules абсолютны: *«Units that are taken in an allied detachment can never make use of
the 'Objective secured!' rule.»* **Способность попадает к юниту тремя путями**, и закрыть один
из них недостаточно:

1. автоматическая выдача каждому выбору Troops (`resolver.ts`);
2. сила Eldar Exarch **Stand firm**, через `EXARCH_POWER_EFFECTS.unitAbility`;
3. **любой предмет арсенала, в описании которого способность взята в кавычки** — общий разбор способностей в кавычках в
   `equipMods` подхватывает их, так что Grey Knights Mandulian Reliquary выдаёт её без
   отдельной привязки.

Четвёртый кажущийся путь — текст: двенадцать `notes` архетипов обещают способность и ничего не дают.
Они остаются, а `ArmyConfig.tsx` добавляет под ними оговорку для союзного детачмента.

```
npx tsx scripts/check_objective_secured_allies.ts
```

**Условие должно проверять `factionSource` относительно АКТИВНОЙ союзной фракции, а не `factionSource`
одно:** юнит добавленного дополнения (Assassins, Horus Heresy) несёт собственный `factionSource`,
не будучи союзным детачментом в смысле правил, и сохраняет способность. Guard проверяет
этот случай, и именно его ломает небрежное исправление, пока все остальные проверки проходят.

**Добавляя здесь пробу, задавайте `slot` в записи ростера.** `RosterEntry` несёт собственный слот,
и `effectiveSlot` читает его, а не `unit.slot` — первый запуск этого guard провалил собственный контроль
Troops из-за этого, и именно для этого контроль и нужен.

### Союзники: матрица и союзный детачмент (`check_ally_matrix_vs_core.cjs`, `check_allied_rules.ts`)

Раздел «Allies» в Core Book даёт конструктору списков четыре вещи; остальное (ауры, какой
транспорт кого может везти, проверка Leadership Desperate Allies) происходит за столом.

```
node scripts/check_ally_matrix_vs_core.cjs "<core rules text dump>"
npx tsx scripts/check_allied_rules.ts
```

Первый сравнивает все 289 ячеек `src/data/alliedMatrix.ts` с сеткой 17×17 из книги правил.
**Следите за шаблоном столбцов при правках:** `SM` без левой границы совпадает внутри `CSM:'R'`,
из-за чего первый запуск показал 13 неверных ячеек, все в столбце SM, на корректных данных.
Семь архетипов ПЕРЕПИСЫВАЮТ строку матрицы; у них свой guard —
`check_ally_matrix_overrides.ts`.

Второй проверяет союзную мини-AOP по списку Core Book и что уникальный / «один раз на армию»
выбор по-прежнему считается один раз, когда вы берёте союзником собственную фракцию. **Если вы пишете пробу с
союзной записью, задайте FactionData карту `allied`** — `resolveUnit` отправляет союзный предмет в
`data.allied[factionSource]`, и без неё каждый союзный юнит разрешается в `undefined`, так что проверки
их пропускают, а молчаливое «нет ошибки» читается как баг движка. Оба контроля в этом guard существуют
именно по этой причине: одна копия должна быть допустимой, а две в основной армии — помечены.

### Отображение психосил (`scripts/check_psychic_display.ts`)

Запись ростера хранит силы, молитвы и пакты как **голые строки имён**; все детали правил
(дальность, цель, значение каста, длительность, эффект) лежат в психоданных и разрешаются при отрисовке
в `src/utils/psychicFormat.ts`. Сломать это можно двумя способами, и каждый невидим для проверки,
которая тестирует только другой:

- **Пул, который поиск не просматривает.** `GENERAL_DISCIPLINES` (`src/data/generalDisciplines.ts`)
  **не входит в `FactionData`** — это шесть дисциплин, из которых может выбирать любой псайкер
  в игре. Их нужно явно добавить в пулы `findPowerByName`. Когда-то этого не было, и все 31
  силы не разрешались ни во что во всех 19 фракциях.
- **Место отрисовки, которое никогда не вызывает форматтер.** Их четыре: `PsychicModal`, `UnitCard`,
  `PrintView` и `PlayView` (боевой вид). Карточка юнита когда-то форматировала молитвы и пакты, а
  силы печатала голым именем.

```
npx tsx scripts/check_psychic_display.ts
```

Он проверяет обе половины: каждая из ~808 выбираемых сил разрешается в непустую мета-строку,
**и** каждое место отрисовки действительно вызывает форматтер — предварительно с вырезанием комментариев, потому что
комментарии в компонентах называют те самые функции, которые ищет проверка. **Запускайте после добавления
дисциплины, файла психоданных или нового места, где отображается сила.**

### Типы юнитов из Core Book (`scripts/check_unit_types.ts`)

Раздел Core Rules «Unit Types» в основном описывает **действия в игре** — Tank Shock, секторы огня,
Vehicle Damage Chart, Hover Mode — и эта часть правильно живёт в вики как текст. Четыре его
утверждения меняют то, чем владеет **конструктор ростера**, и этот guard проверяет эти четыре на всех
670 датащитах:

- **Monstrous Creature и Monstrous Infantry не могут садиться в транспорт.** Оба говорят это в разделе
  Movement. Осторожно: `"Monstrous Infantry"` **содержит слово «Infantry»**, так что проверка
  `unit_type.includes('infantry')` читает его как разрешение. Это был настоящий баг для 33 юнитов.
- **`is_monster` означает Monstrous *Creature*** (или Gargantuan), но никогда не Monstrous Infantry. Каноном
  служит заголовок цен на каждом листе Army Customisation: `NORMAL | CHARACTER MODELS | MONSTROUS
  CREATURES & VEHICLES`. Флаг выбирает этот третий столбец, так что установка его Monstrous Infantry
  оценивает и фильтрует юнита как существо.
- **Ни у одной техники не печатается значение Leadership** — «Vehicles automatically pass Leadership tests as they
  do not have a Leadership value.»
- **Каждый Walker несёт `is_vehicle`** — «Walker: Acts like Vehicles.» Это важно, потому что каждое
  условие для техники в движке (доступ к арсеналу, область черт, HP вместо W, очки) читает **флаг**, а не
  строку `unit_type`. Flyer, у которого `unit_type` не содержит «Vehicle», а `is_vehicle` истинно,
  поэтому **верен**, а не ошибочен.

```
npx tsx scripts/check_unit_types.ts
```

**Запускайте после правки `unit_type` любого датащита или его флагов `is_vehicle`/`is_monster`/`is_character`,
либо после правок `transportGate.ts`.** Завершается с ненулевым кодом и называет каждого нарушителя. «Gains Deep Strike»
у Jump Pack Infantry — пятое утверждение, принадлежащее конструктору, и у него свой guard,
`scripts/check_jump_pack_deep_strike.ts`.

### Экспорт в Tabletop Simulator

Армию, собранную здесь, можно экспортировать на стол Tabletop Simulator. Это две половины, которые нужно
менять вместе:

| Файл | Задача |
|---|---|
| `src/utils/ttsExport.ts` | Строит данные и скачивает их (кнопка **TTS** в версии для печати) |
| `tts/Custom40k.lua` | Мод: читает эти данные и создаёт карточки |

**Мод намеренно не содержит кодекса.** Приложение сначала разрешает армию — через ту же
`resolveUnitProfile`, что использует карточка юнита и версия для печати — так что отправляются
итоговые характеристики, итоговые профили оружия и настоящий текст правил. Lua никогда не должен знать правило Custom40k,
и обновление кодекса никогда не означает повторную загрузку предмета в Workshop. Так и оставляйте: если вы
собираетесь добавить в Lua логику правил, исправление относится к экспорту.

`TTS_SCHEMA` (TypeScript) и `SCHEMA` (Lua) должны совпадать; повышайте обе вместе при смене формы данных.

**Схема 2 (экипировка).** Юнит, чьи модели несут разное снаряжение, экспортируется как одна запись `models[]` на каждую экипировку, у каждой целое число `count` и список `modelWeapons`, указывающий на `weapons[].id`. Разделение делает `splitGroup()` в `ttsExport.ts`; она читает группы оружия резолвера, так что неверное количество там — проблема резолвера или таблицы, а не экспорта. После правок запустите `npx tsx scripts/_tts_sweep.ts` (каждый юнит × каждая одиночная опция × два размера; он печатает, какие юниты получаются с `loadoutsExact: false` и почему) и `npx tsx scripts/_tts_one.ts <фракция> "<юнит>" '<optionQty json>'`, чтобы посмотреть на один.

**Lua протестирован — запустите тест, прежде чем его трогать.** В TTS нет headless-режима, поэтому скрипт
запускается под виртуальной машиной Lua `fengari` с заглушками глобальных функций TTS, на настоящем экспорте:

```
npx jiti tts/test/makeExport.ts "Codex/<сохранённая армия>.json" army.json
node tts/test/run.cjs army.json          # добавьте --dump, чтобы прочитать отрисованные карточки
```

Первый запуск поймал четыре бага до того, как файл попал в игру; хуже всего было то, что `ipairs` в Lua
останавливается на первой дыре `nil` в литерале таблицы — это молча удаляло строку
дальности/цели/длительности каждой молитвы, ломая заново именно то, что v1.70 только что исправила. См. `tts/README.md`.

### Названия катаканой (`src/utils/localName.ts`, `src/data/names.ja.json`)

Японский игрок попросил названия катаканой. **Данные никогда не переводятся**: названия юнитов, оружия и опций — это ключи, по которым сопоставляет движок, поэтому их изменение молча сломало бы правила и сохранённые списки. Название превращается в катакану только в момент **отрисовки** и только когда язык японский: `nm(w.name)` для названий, `rl(w.type)` / `rl(w.abilities)` для типов оружия и способностей, `eqText(equipped_with)` для строки экипировки.

- `names.ja.json` — это `{ "английское в нижнем регистре": "катакана" }` (~4 500 записей) и **отдельный лениво загружаемый чанк** — остальные четыре языка его никогда не скачивают. Неизвестное ему имя показывается по-английски, никогда не пустым.
- `jaName()` понимает также `Plasma gun - Standard`, `Plasma gun (Standard)`, `A and B`, `Two lascannons`, `The X` и конечный глиф-маркер (`ᴹ`).
- Строка экипировки переводится **по шаблону**, а не предложение за предложением (98% имеют рамку `Every X is equipped with: A; B.`), на всех пяти языках; названия меняет только японский. Предложение, не подходящее к рамке, показывается как написано.
- Чтобы добавить имя, добавьте строку в таблицу и запустите `npx tsx scripts/_ja_names_test.ts`: он сообщает для каждого юнита, модели, оружия и опции в игре, что всё ещё по-английски.
- Новому месту, где рисуется имя, нужен `nm()` вокруг него; больше ничего.
- **Вики** переводит во время сборки через `wiki/src/lib/loc.ts` (`wn` имена, `wr` типы оружия и способности, `wp` подписи и предложения, набранные на странице, `wPhrase`, `wRange`, `wEquipped`, `wUnitType`, `wSlot`) и таблицу подписей `wiki/src/lib/phrases.ts`. Она использует чистые помощники приложения (`src/utils/localName.ts`, `jaProse.ts`, `unitTypeLabel.ts`) и `src/data/names.ja.json`, копируемые `wiki/scripts/vendor.mjs`; общие психические дисциплины тоже берутся из приложения (раньше в вики была копия, и она разошлась). Запустите `node wiki/scripts/vendor.mjs` перед `node wiki/scripts/build-all.mjs`, иначе вики соберётся с копиями прошлой сборки. Никогда не набирайте английский текст на странице вики: добавьте строку в `phrases.ts`.
- У остальных английских данных движка свой помощник отрисовки, никогда не сырое `{x.name}`: слоты — через `slotLabel(lang, slot)` (`src/utils/slotLabel.ts`), типы юнитов — через `unitTypeLabel(lang, type)` (`src/utils/unitTypeLabel.ts`), названия форматов игры и строки правил — через `engName`/`engNotes` (`src/utils/engagementText.ts`), тип/цель/длительность психосилы — через `powerMetaLine` (использует таблицу текстов), а сообщения валидатора получают значения `{slot}`/`{unit}` локализованными внутри `T()` в `src/engine/validators.ts`. Жёстко прописанная английская подпись в компоненте — это баг: вместо этого добавьте ключ в `src/i18n` (все пять языков).
- **Заголовки групп опций** (`g.header`, предложение над каждым блоком опций) переводятся предложение за предложением через `localiseAbility()` и `src/data/abilityTexts.<язык>.json` по хешу английского текста, точно так же, как текст правила. У заголовка, который таблицы переформулировали, нет перевода, пока его не добавят; `npx tsx scripts/_headers_test.ts` перечисляет каждый заголовок в игре без перевода на каждом из четырёх языков.

### Gitfinda — поиск игры (`api/_lib/gitfinda.js`, `src/components/GitfindaModal.tsx`)

Доска, где игроки публикуют «хочу сыграть» (армия, Skirmish / Pitched / Epic, очки, часовой пояс IANA и время, когда они свободны), другие просматривают и нажимают **Match**, и у каждого матча появляется личный чат. Сделано по документу требований Dominic; **бета** — см. `ki-gitfinda-beta-scope-01`, что она намеренно пока не делает (нет email, нет блокировки).

| Файл | Задача |
|---|---|
| `api/_lib/gitfinda.js` | **Все правила и весь SQL.** Получает `sql` параметром вместо импорта, чтобы его можно было тестировать на настоящем Postgres |
| `api/gitfinda/[action].js` | Тонкий маршрут: аутентифицирует вызывающего, выбирает действие, превращает `Refusal` в JSON. Это **12-я и последняя** функция Vercel, которую позволяет план Hobby — перед добавлением новых слейте один маршрут в другой |
| `src/components/GitfindaModal.tsx` | Просмотр, создание, мои объявления, мои матчи + чат |
| `src/lib/gitfindaTime.ts` | Часовые пояса: слот вводится как настенное время в поясе автора, хранится как момент, показывается пересчитанным |
| `public/gitfinda/*.png` | 9 чистых иконок из набора макетов. Эмблемы фракций из набора НЕ использовались (в его README предупреждают, что они могут напоминать существующую символику) — для армий используется `public/faction-symbols/` |

Что легко сделать неправильно:

- **Хранятся только `active` и `cancelled`.** *Expired* (все слоты прошли) и *Matched* (кто-то откликнулся) выводятся при чтении — нет задачи, которую нужно запускать, и нечего синхронизировать.
- **Отказ несёт ключ перевода** (`gfErrArmy`, …), который браузер подставляет, чтобы игрок прочитал его на своём языке. Новому отказу нужен ключ в `src/i18n/index.ts` (en, de, es) и в `ru.json` / `ja.json`.
- **Никогда не кладите `t` или встроенный колбэк в зависимости хука.** `useT()` возвращает новую функцию при каждом рендере; так эффекты перезапускались бесконечно (бесконечный цикл запросов и чат, который сам очищался). Компонент хранит последние значения в ref (`useLatest`).
- **Список армий в браузере — копия серверного** (`GITFINDA_ARMIES` / `ARMIES`); тест падает, если они расходятся.

**Объявления в Discord.** Когда кто-то публикует игру, `discordNotifier` может отправить короткое сообщение в Discord сообщества через webhook (`GITFINDA_DISCORD_WEBHOOK` в Vercel; **не задано = выключено**, а URL — секрет: никогда не вставляйте его в issue или чат). Идентификатор сообщения хранится в `gitfinda_posts.discord_message_id`; `discordRemover` удаляет собственное сообщение webhook, когда игра отменена, сыграна по матчу или истекла (404 считается удалённым). Свободных слотов cron не осталось, поэтому **sweep** удаляет сообщения завершённых игр по несколько штук всякий раз, когда кто-то пользуется доской (не чаще раза в 30 с на экземпляр сервера), а `dropUserAnnouncements` запускается перед тем, как админ удалит аккаунт (объявления удаляются каскадом, и идентификаторы были бы потеряны). Ссылка в сообщении — `/?gitfinda=<id>`: `App.tsx` открывает именно эту игру после входа.

Тесты — запускайте оба после любых правок:

```
npm i --no-save @electric-sql/pglite      # один раз; Postgres только для разработки, работает в памяти
node scripts/_gitfinda_test.mjs           # каждое правило на настоящем SQL (118 проверок, включая Discord-уведомитель, удаление, sweep и удаление аккаунта)
npx tsx scripts/_gitfinda_time_test.ts    # математика часовых поясов, включая края перехода на летнее время
```

`_gitfinda_test.mjs` проверяли, намеренно ломая код (убрав проверку владельца, уникальный индекс…), и он падал там, где должен; делайте так же, когда добавляете правило.

### Когда править файлы наследий

`legacies.ts` (верхнего уровня) — тонкий межфракционный диспетчер: он управляет тем, **какие дисциплины и молитвы показывает психическое окно** в зависимости от активного наследия, и какую дополнительную силу наследие всегда даёт. Собственные данные наследий каждой фракции (правила доступа к арсеналу, ограничения меток, карты дисциплин/молитв) лежат в `codex_<faction>/legacies.ts` этой фракции и читаются через диспетчер.

- **`codex_space_marines/legacies.ts`** — правьте, если:
  - вы добавляете новую дисциплину наследия SM, которая должна быть закрыта условием (добавьте в `SM_LEGACY_DISC_MAP`, сопоставляющую название дисциплины → требуемое наследие).
  - вы добавляете новую молитву, появляющуюся только с Legacy of the Crusader (добавьте в `SM_CRUSADER_PRAYERS`).
  - вы переименовываете существующее наследие или дисциплину SM.
- **`codex_grey_knights/legacies.ts`** — правьте, если меняете, какую силу наследие всегда даёт псайкерам GK (`getGKLegacyPower`).
- **`codex_genestealer_cults/legacies.ts`** — та же механика для GSC: каждое наследие обучает каждого псайкера одной дополнительной силе (`getGSCLegacyPowerName`). Он хранит только ИМЯ наследие → сила; текст силы берётся из собственной дисциплины кодекса «Legacy Psychic Powers», так что никогда не копируйте текст сюда.
- **`codex_<faction>/legacies.ts`** — правьте для правил доступа к арсеналу наследия или ограничений меток фракции (например, `CSM_LEGACY_NOTES` в `codex_csm/legacies.ts`).

Если вы добавляете новую фракцию с дисциплинами, закрытыми наследием, создайте файл `codex_<faction>/legacies.ts` по тому же образцу, подключите его в `PsychicModal.tsx` и зарегистрируйте в карте `FACTION_LEGACY_NOTES` верхнеуровневого `legacies.ts`, если нужен ещё и вывод структурированных заметок.

### Структура данных (папки по фракциям)

Данные фракции лежат в `data/parsed/<faction>/` — одна папка на фракцию, а не плоский каталог монолитов.

      mark_khorne.json   Арсенал по метке (только фракции Хаоса)
      legion_*.json      Арсенал наследия/ордена (по файлу на наследие)
    psychic/
      disciplines.json   Массив психических дисциплин
      prayers.json       Молитвы/инвокации
      pacts.json         Игровые механики (например Blood Tithe, таблица Daemonkin)
      daemonkin.json     Таблица призыва Daemonkin
    archetypes.json      { archetypes[], legacies[], traits[] }
    animosity.json       { animosity, allied }   <- только CSM/CD (таблица вражды меток)
    unit-notes.md        комментарии из шапок, которые несли старые .ts-файлы
  space_marines/         (та же структура, без marks/animosity.json)
  horus_heresy_legiones_astartes/, horus_heresy_forces_of_the_machine_god/   два дополнения (units/ + supplement.json)

### Структурированные эффекты правил и примитивы стоимости (добавлено в v0.51–v0.52)

Некоторые правила нельзя выразить одним текстом описания — им нужны структурированные поля, которые читает движок. **При выборе поля смотрите на ГЛАГОЛ датащита.**

- **`OptionEffect`** (`types/data.ts`) — несётся в `Choice`, `OptionGroup` **или `ArmoryItem`** (`item.effect`). Поля:
  - `stat_mod: [{ stat, delta }]` — например `+6" M` от jump pack.
  - `adds_unit_types: string[]` — **добавляющее** получение типа. Глагол «**gains** the unit type X». Модель сохраняет существующие типы.
  - `set_unit_type: string` — **замена** всей строки типов. Глагол «**change** unit type **to** X».
  - `grants_abilities: string[]` — выданные особые правила (только то, что указано в датащите).
  - Эффекты применяются в `resolver.ts` (`applyEffect`) и **дедуплицируются относительно базового профиля модели** — тип или способность, которые у модели уже есть, не добавляются повторно. Характеристики и способности в кавычках у предмета арсенала по-прежнему берутся из `equipMods` (разбор описания); `item.effect` несёт только смену типа.
  - **Тип и способность — не одно и то же.** `"Jump Pack Infantry"` — это ТИП юнита (даёт Deep Strike); `"Jump pack"` — это СПОСОБНОСТЬ (не даёт). Моделируйте то, что буквально сказано в датащите.
- **`OptionGroup.per_model`** — ставьте `true` на inline-опцию ИЛИ обычную группу `choices[]`, чей датащит говорит «for +X points **per model**» (или «...receive one of the following upgrades **per model**»). Тогда движок очков берёт `inline_pts × размер юнита` (inline) или `choice.points × qty × размер юнита` (choices) вместо одного раза за весь юнит. Разовые inline-опции (повысить одного Sergeant) и группы «every model may swap X» (чей `qty` уже равен выбранному числу) оставляйте без неё.
- **`equipMods.ts`** — разбирает `+stat`, сейвы и способности в кавычках из `desc` предмета арсенала. Он пропускает слова типов юнита в кавычках (их обрабатывает система типов) и дедуплицирует выданные способности относительно базовых способностей юнита.
- **Лимиты снаряжения в Skirmish** находятся в `validators.ts` (внутри блока `eng.statCaps`). Они обеспечивают ограничения из дополнения Missions: нельзя получить 2+ броню, 4+ или лучше инвуль, T8+, оружие с Damage 3 или более одного Unique предмета арсенала — всё это основано на документах Missions и Core Rules (`Codex/*.docx`). Новые лимиты добавляйте сюда, а не в интерфейс.

> **Кодировка (mojibake):** при ручной правке данных JSON или TS сохраняйте файлы в UTF-8. Искажённые последовательности вроде `â€"` (должно быть `—`) появляются при копировании и вставке; `scripts/_scan_mojibake.cjs` их находит. Не вставляйте из редакторов с форматированием.

> **Проактивная проверка багов:** `scripts/sanity_sweep.ts` напрямую импортирует настоящие модули данных/движка (запуск `npx tsx scripts/sanity_sweep.ts`, установка не нужна) и помечает структурные красные флаги, не дожидаясь сообщения игрока: мёртвые группы опций (`choices: []` при ограничении, ждущем настоящих вариантов), противоречия `is_character`/`unit_type`, висячие ссылки на имена юнитов в `engine/archetypes`, висячие записи `slot_to_units`, `replaces`, называющий оружие, которого нет у юнита, висячие ссылки `variant_link` и повторяющиеся названия оружия в одном юните. Это структурная проверка, а не проверка правил — каждое срабатывание всё равно требует человеческого чтения, прежде чем считать его подтверждённым багом (известные формы ложных срабатываний см. в комментариях в шапке скрипта). Перезапускайте после любой правки данных, затрагивающей эти поля, и особенно перед релизным push.

> **Синхронизация канона:** `scripts/fetch_codex.cjs` скачивает каждую таблицу фракции прямо из Google Sheets автора (ссылки лежат в таблице гиперссылок внутри `Codex/Custom40k Core Rules.docx`) и сообщает, какие из наших копий `Codex/*.ods` устарели, вкладка за вкладкой. Запустите без аргументов, чтобы обследовать всё, или назовите фракции, чтобы проверить только их. `--apply` перезаписывает нашу копию — намеренно по запросу и по одной фракции, потому что **замена .ods означает, что эта фракция снова не проверена и требует полного прохода** (см. правило ниже). Никогда не применяйте массово.

> **Синхронизация ДОКУМЕНТОВ ПРАВИЛ:** `fetch_codex.cjs` покрывает таблицы фракций и ничего больше, поэтому долгое время три книги правил могли устаревать без какого-либо сигнала — и устаревали: наша копия Core Rules лежала на 1.262, пока живой документ ушёл на 1.264. `scripts/fetch_docs.cjs` это закрывает. Он забирает Core Rules, Missions и Planetary Assault из их живых Google Docs, сравнивает ИЗВЛЕЧЁННЫЙ ТЕКСТ, а не байты файла (Google каждый раз экспортирует другой zip, так что равенство байтов показывало бы изменение при каждом запуске), печатает `Rules version` каждого документа и завершается с ненулевым кодом, если любой из них отличается. `--write` заменяет устаревшие копии. Запускайте рядом с `fetch_codex.cjs` перед любой работой, затрагивающей текст правил — правило, процитированное из устаревшего документа, хуже отсутствия ответа, потому что выглядит верным.

> **Аудит фракции по её таблице:** `scripts/ods_audit.cjs "Codex/<faction>.ods" <папка фракции>` сравнивает таблицу с боевыми данными юнит за юнитом — строки моделей (имя / min / max / характеристики / очки), профили оружия, фразу `equipped_with` и названия и цены вариантов в группах опций — и печатает различия, ничего не записывая. Добавьте имя юнита третьим аргументом, чтобы проверить только его. Прочитайте каждую строку и решите по каждой: таблица побеждает по ФАКТАМ, боевые данные побеждают по СЕМАНТИКЕ, а собственные опечатки автора (лишняя точка в конце, скопированное имя юнита) тоже здесь видны. Один артефакт таблиц он уже обрабатывает: ячейка `No.` со значением `4-19` хранится как ДАТА, поэтому инструмент читает отформатированный текст, а не сырое серийное число — не «исправляйте» это в таблице.


### Журнал изменений и известные проблемы (важно — разделены с v0.47)

Эти два файла служат разным целям, и их нельзя путать:

| Файл | Что сюда идёт |
|---|---|
| `src/data/changelog.ts` | История версий — одна запись на релиз; английский в `changelog.ts`, остальные четыре языка в `changelog.i18n.json` |
| `src/data/known-issues.ts` | Учёт багов и ограничений — статус может быть `known`, `investigating`, `fixed`, `by_design` или `planned` |

**До v0.47** оба жили в `changelog.ts`. Теперь они раздельны. Если вы исправили известный баг:
1. Откройте `src/data/known-issues.ts`, найдите проблему по `id` и поставьте `status: 'fixed'`.
2. Добавьте строку в текущую запись версии в `src/data/changelog.ts` с описанием исправления.

**Не** правьте `changelog.ts` для обновления статусов проблем — в нём больше нет `KNOWN_ISSUES`.

Домашние правила мейнтейнера, чтобы PR на них не споткнулся:

- **Новая версия выпускается, только когда так скажет мейнтейнер**; `CHANGELOG[0].version` — номер версии.
  Дополнительные исправления идут в текущую запись (не больше двух записей в день, сгруппированных по теме).
- **Объявление на главной показывает только собственные исправления текущей версии**, одна клауза на строку, на всех пяти
  языках. Повышение `ANNOUNCEMENT_KEY` показывает его заново всем, кто его закрыл, поэтому изменение стиля
  его не повышает.
- **Записи журнала изменений старше 30 дней время от времени удаляются** (git хранит историю); исправленные Known Issues
  такого возраста скрываются.
- **Текст журнала изменений всегда сначала на английском**; всё, что игрок будет пересылать (вопрос автору),
  пишется простым английским.

### События и лиги (`api/events/[action].js`, `src/components/EventsModal.tsx`)

События и лиги под управлением организатора, сделанные по документу требований автора. Три таблицы:
`events`, `event_players`, `event_games`.

Три вещи, которые дизайн решает заранее, чтобы их не пересматривать на ревью:

- **Событие и лига — это одна и та же строка.** Всё, кроме турнирной таблицы, одинаково, поэтому
  `is_league` лишь решает, генерируется ли таблица. Отдельная таблица продублировала бы
  регистрацию, одобрение и назначение списка.
- **Сообщённая игра не засчитывается, пока её не подтвердит СОПЕРНИК**, и подтвердить может только соперник —
  не организатор, иначе подтверждение ничего бы не значило. Отклонённый отчёт становится `disputed`
  и остаётся видимым организатору, а не исчезает.
- **Турнирная таблица выводится, никогда не хранится.** Хранимая таблица расходится в тот момент, когда игра оспорена или
  исправлена, и здесь ничего не настолько дорого, чтобы кэшировать.

`is_test` и действие `reset-test` существуют потому, что функцию предполагается сначала запускать закрытой, с
придуманными игроками и списками, а затем очищать перед открытием. Эта очистка — настоящая операция с первого дня,
а не ручная чистка базы данных.

шаблону, что у Campaign.

### Лимит в 12 функций (`api/`)

План Hobby у Vercel ограничивает деплой **12 serverless-функциями**, и `api/` находится ровно на 12.
Файлы в `api/_lib/` импортируются, а не маршрутизируются, поэтому не считаются. Поэтому несколько роутеров
— это файлы `[action].js` с `switch`, а не по файлу на endpoint.

Добавление нового endpoint означает, что **сначала нужно освободить слот**. Проверьте так:

```bash
find api -name "*.js" -not -path "api/_lib/*" | wc -l
```

### Справки rules-model (`src/data/rules-model/<faction>.md`)

У каждой проверенной фракции есть Markdown-справка в `src/data/rules-model/` (шаблон: `_TEMPLATE.md`).

датащитов по слотам и проверка пробелов движка — всё проверено по каноническому исходному HTML и
боевому JSON. Это справочные документы для контрибьюторов и движка — приложение их не загружает.
Когда вы проверяете или исправляете данные фракции, обновляйте её справку, чтобы она оставалась синхронной.
Межфракционные дополнения используют ту же папку и именование (например `escalation.md` для
дополнения Escalation / Lords of War).

### Переводы

## Автообновление юнитов (кнопка Inquisitor)

`UnwiseGetData/update_units.py` скачивает Google-таблицу каждой фракции (`factions.csv` перечисляет идентификаторы таблиц) и переписывает **принадлежащие таблице** ключи каждого файла юнита в `data/parsed/<faction>/units/` — name, models, variant models, min cost, default size, equipped with, weapons, abilities, unit type, is_monster и keywords. Он никогда не создаёт юниты и никогда не трогает `option_groups`, флаги (`has_armory_access`, `is_character`, …), арсенал, архетипы, психосилы и молитвы.

- **Запуск из приложения:** панель Inquisitor → Factions → *Unit auto-update* → **Run unit update**. Это запускает `.github/workflows/update-units.yml` (GitHub Actions), который выполняет скрипт, затем `scripts/check_unit_update.cjs` (блокирующие проблемы: невалидный JSON, нетекстовые способности, потерянный ключ `variant_models`, пустые модели) и `scripts/sync_codex_versions.cjs` (сдвигает значок версии в `src/data/factionCatalog.ts`, когда изменилось название таблицы), собирает приложение и открывает **pull request**. Ничто не попадает в `main`, пока человек его не слил.
- **Настройка сервера (один раз):** проекту Vercel нужен `GITHUB_DISPATCH_TOKEN` (fine-grained токен для этого репозитория с правом *Actions: read and write*); репозиторию нужна настройка *Settings → Actions → General → Allow GitHub Actions to create and approve pull requests*.
- **Локальный запуск:** `cd UnwiseGetData && python update_units.py` (Python 3.12+; `pip install openpyxl pandas requests simplejson`), затем `node scripts/check_unit_update.cjs`.
- Файл в `data/parsed/.../units/` должен называться по имени юнита (`foetid_virion.json`), иначе скрипт его не найдёт.
- Он охватывает 19 кодексов **и** два дополнения Horus Heresy (их папки; ключи приложения остаются `horus_heresy` / `legio_titanicus`). Каждой таблице нужна строка в `UnwiseGetData/factions.csv`, а название вкладки длиннее 31 символа должно быть в списке слишком длинных названий скрипта.
- **Проверки pull request висят в состоянии «action required»**, потому что его открыл бот: мейнтейнер одобряет запуск (или меняет *Settings → Actions → General → Fork pull request workflows*), затем сливает. Тело PR перечисляет, юнит за юнитом, что изменилось.
- **Обновление юнитов, ухудшающее карточку, — вопрос к таблице** (таблица, которую скрипт режет на одну способность на ячейку, заголовок оружия без `*`, опция обмена, у оружия которой нет строки). Сообщите автору с вкладкой и строкой; не правьте файл юнита вручную, следующее обновление это отменит. Таблицы способностей Orks — рабочий пример: теперь они приходят как одна способность со строками на отдельных линиях, а текст способностей сохраняет переносы строк на карточке и в версии для печати.
- `node scripts/fetch_codex.cjs --apply <faction>` перезаписывает нашу локальную копию `Codex/*.ods` и помечает фракцию как непроверенную; не запускайте его просто чтобы посмотреть.
